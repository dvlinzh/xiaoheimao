WHAT

一个插件，三种身份

数据中枢、AI 能调用的工具、看得见的猫——三层互相独立，坏掉任何一层都不影响另外两层。

🗂️ 数据中枢

所有 AI 工具把想法写进同一个地方 ~/.mind-board/。纯 JSON 文件 + 原子写盘，没有数据库、没有云端、没有账号。

🔌 MCP 工具

三个标准工具——organize 整理、query 回看、control 管理。任何支持 MCP 的 AI 工具都能调用。

🐱 桌宠壳

小黑猫蹲在任务栏，头顶图标环显示哪些 AI 在干活；点开漫画风面板，四层骨架一目了然。

核心玩法：四层骨架

AI 把对话内容随手归入四层——每层有明确的判定标准，聊天照常进行，沉淀悄悄发生。

METHODOLOGY

整理方法论

板子的价值 = 信息密度。这一章是 AI 整理时遵循的全部规则——也是你自己手动整理时的参考。

① 这句话该进哪层？——判定决策树

拿到一段值得记的话，按顺序问三个问题，落到唯一的一层。判断标准是内容的成熟度，不是话的长短。

有明确判断？「X 应该这样」/「已确定 Y」
还是在选做什么？候选路线 / 待拍板的选项
还是没验证的问号？说不出边界、需要回头确认
回答去层含义
判断成型了要点 points重点预览，可带 link 指向完整版
还没成型想法 ideas愿景层——过程与任务不进这里
在选做什么方案 plans候选路线，采用全局唯一
没验证的问号缺口 gaps写成可回答的问题

② 什么值得记？——信噪比三问

每条入库内容都要过三问，任何一问不过就不记。「乱七八糟」的板子几乎都是三问失守的结果。

① 是结论还是过程？过程口水没有信息量。
✗ "我检查了一遍日志"
✓ "日志确认钩子没被调用"
② 三天后还指导行动吗？被取代的中间态该退场（supersedes）。
✗ 已修复的猜测与最终结论并排
③ 说得出边界吗？说不清适用条件 = 半个结论。
✗ "要加缓存"
✓ 进缺口："缓存策略待定"

③ 什么时候记？——时机与节奏

规则内容理由
批量不流水一轮对话最多一次 organize，打包提交本轮全部条目逐句入库 = 流水账；对话的自然单元是「一轮」
节奏可调整理频率 1/2/3 轮一档，到点钩子才提醒催促本身也是上下文成本
回答优先整理是副业：先正常回答，工具调用安静完成打断感是这类工具的头号死因
过程与结论分离调试发现只在构成结论时入库；旧结论被取代时用 supersedes 退场板子只保留当前有效认知

④ 缺口管理：会提问才会收敛

缺口是唯一「主动消耗注意力」的层——写得好驱动项目前进，写得烂变成待办坟场。

规则说明
写成可回答的问题✓ "LRU 在写多读少场景命中率未验证" · ✗ "还要优化优化"——无法回答的缺口永远关不掉
一轮最多追问一个AI 补缺口时挑最关键的问用户；连环追问是打扰
谁都能关任何 harness 发现缺口已解决即可标记——不需要是提出者
14 天衰减超两周未动的缺口自动划线降调——要么过时了，要么值得重写
拒绝伪缺口"待优化""待确认"这类没有主语的不收

⑤ 更新、替代还是新建？——收敛三选一

情形动作例
语义没变，措辞变了直接提交——bigram ≥0.7 自动命中旧条目更新「支持深色模式」→「深色模式支持」
结论被细化直接提交——细节合并进旧条目「深色模式要做」→「…先做编辑器」
结论被推翻supersedes 替代——旧条目退场（保留可审计）「不做动画」→「动画要做，Lottie 方案」

方案层的定位是「承诺层」：落地确认后毕业——认知沉淀为要点、关闭它填充的缺口，方案保留为决策档案。

⑥ 项目生命周期

阶段判定该做什么
draft 构思目标未定或骨架近空先聊目标，AI 协助收成一句话目标
clarifying 推进目标已定，缺口在收敛正常整理；优先追问缺口；方案竞争到唯一
reflected 已沉淀结论齐了、缺口清了点「归档」折叠出活跃列表，数据永久保留
archived30 天无活动自动标记仪表盘勾「含已沉淀」可见，「恢复」随时拉回

⑦ 多 harness 协作规则

场景规则
共享板项目身份 = 目录。两个工具在同一目录工作 → 同一块板，互相可见全部沉淀
接手礼仪后接手的工具先 mind_board_query 看板子再动手——钩子状态行就是为此设计的
竞争收敛不同结论 → 后写的 supersedes 前写的；真是并立的两案 → 都进方案竞争
缺口责任谁发现谁立，谁都能关；跨工具缺口写明对象
参与者可见项目档案 harnesses[] 记录全部参与者；图标环 / 面板 / 仪表盘按此归属显示

⑧ 反模式清单（每一条都真实发生过）

反模式后果
逐句流水账入库板子变成对话备份，信息密度归零
已解决的猜测和最终结论并排三天后分不清哪个是对的
伪缺口堆积缺口层失去驱动力，变成待办坟场
方案层多个「采用」并存「当前押注」语义失效（系统强制全局唯一）
过程性任务进想法层愿景层被稀释，蓝图看不见了
TECH

技术路线图

核心思路一句话：把「聪明」放进数据协议，把「脆弱」隔离在可抛弃的壳里。 文件系统是唯一事实源，三条标准通道接入，AI 工具、钩子、桌宠互不依赖。

1

软约束注入，不烧上下文。会话开始注入一次完整协议；之后每轮只注一行状态，比反复塞全文省约 95% 上下文。

2

目标漂移防护是硬的。AI 写入的目标与现状相似度过低时，中枢拒绝写入并要求 AI 先问你——prompt 管不住的，用协议机制管。

3

文件即数据库。原子替换保证崩溃安全，任何编辑器都能直接修数据，拷走目录就是完整备份。

4

壳坏了不伤数据。渲染层的猫、图标环、面板可以随时重写；AI 通道（MCP + 钩子）独立工作——这条经验来自上百次真实重启。

整理流水线（store.mjs · organize）

窗口编排与稳定性

五个透明置顶窗（猫 / 图标环 / 面板 / 设置 / 仪表盘）共用一套交互契约。每条规则背后都是一次真实事故——这一层是全部复杂度的所在，也是所有防御性设计的沉淀处。

机制防的事故
禁用原生遮挡计算全屏应用覆盖后窗口「幽灵可见」——看得见位置点不着
win.setShape 原生穿透切换式穿透的入场竞态：透明区第一击被吞
主进程光标轮询驱动交互系统鼠标钩子被全屏应用摘除且永不恢复
拖拽阈值 10px / 弹环防抖 1.2s手抖误判拖拽、快速连点闪没
show 时强制刷新 + 移除 blur 隐藏隐藏期定时器节流显示旧 DOM；失焦闪没

FAQ

常见问题

会打断我和 AI 的对话吗？

不会。整理是 AI 的「副业」：它先正常回答你，工具调用安静完成。每轮最多一行提醒，你几乎察觉不到它的存在——直到打开面板发现都记下来了。

AI 会不会乱记、记错？

协议要求：模棱两可的一律进「缺口」，不脑补；疑似换目标时中枢直接拒写，强制 AI 先问你。所有条目在面板里可视化，随手拖拽修正。

一个任务多个 AI 工具做过怎么办？

这正是核心设计：项目身份绑定目录而非工具。所有工具共享同一块板，互相可见对方沉淀的全部内容；条目去重保证不重复；方案采用全局唯一表达「当前押注」。详见「整理方法论 ⑦」。

我用的是 Codex / Gemini CLI 怎么办？

它们的 MCP 配置里注册同一个服务命令即可——数据中枢按项目目录自动归档，所有工具共享同一块板子。

占用多少资源？

一个 Electron 壳（约 100–200MB 内存）+ 每轮一行文本的钩子。数据是几个小 JSON 文件，journal 超 1MB 自动轮转。
