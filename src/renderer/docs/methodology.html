整理方法论 · 规则与图解

算法页讲的是「机器怎么处理条目」，这一页讲的是「什么值得记、该进哪层、何时收敛」—— 整理的判断规则。AI 侧的执行版在 src/core/protocol.mjs，本页是它的完整展开。

① 这句话该进哪层？——判定决策树

拿到一段值得记的话，按顺序问三个问题，落到唯一的一层。判断标准是「内容的成熟度」，不是「话的长短」。

② 什么值得记？——信噪比三问

板子的价值 = 信息密度。每条入库的内容都要过三问，任何一问不过就不记。 「乱七八糟」的板子几乎都是这三问失守的结果。

自查问的是不过关的典型
①是结论还是过程？ 过程口水（“我看了下”“试了一下”）没有信息量，只有结论才有 ✗ “我检查了一遍日志” → ✓ “日志确认钩子没被调用”
②三天后还指导行动吗？ 中间态的发现一旦被后续认知取代就该退场（supersedes），不该和最新结论并排躺着 ✗ “素材可能有裁剪问题” （已被定位并修复）与最终结论并排
③说得出边界吗？ 说不清适用条件/范围的判断是半个结论——按协议进 gaps，不硬编 ✗ “要加缓存”（什么粒度？什么策略？）→ ✓ 进 gaps：“缓存策略待定”

③ 什么时候记？——时机与节奏

规则内容理由
批量不流水一轮对话最多一次 organize，把这轮产生的所有条目打包提交逐句入库 = 流水账；对话的自然单元是「一轮」
节奏可调整理频率 1/2/3 轮一档；到点钩子才提醒，平时沉默催促本身也是上下文成本
回答优先整理是副业：先正常回答用户，工具调用安静完成，不长篇旁白打断感是这类工具的头号死因
过程与结论分离调试中间发现只在构成「结论」时入库；旧结论被新认知取代时用 supersedes 退场板子只保留当前有效认知

④ 缺口管理：会提问才会收敛

缺口是板子里唯一「主动消耗注意力」的层——写得好它驱动项目前进，写得烂它变成待办坟场。

规则内容
写成可回答的问题✓ “LRU 在写多读少场景命中率未验证” · ✗ “还要优化优化”——无法回答的缺口永远关不掉
一轮最多追问一个AI 补全缺口时挑最关键的一个问用户；连环追问是打扰
谁都能关任何 harness 在整理中发现缺口已被解决，即可标记 resolved——不需要是提出者
14 天衰减超两周未动的缺口自动划线降调（显示层）——要么真过时了，要么值得重新写成更尖锐的问法
拒绝伪缺口“待优化”“待确认细节”这类没有主语的缺口不收——说不出「回答它」长什么样，就别立这条

⑤ 更新、替代还是新建？——收敛三选一

方案层的定位：承诺层——adopted 全局唯一表达「当前押注」。落地确认后「毕业」：登记 decided 要点（认知沉淀为要点）+ 关闭它填充的缺口（闭环完成），方案本身保留为决策档案——它是「为什么走到今天」的证据。协议规则 12。

⑥ 项目生命周期：draft → clarifying → reflected

阶段判定该做什么
draft 构思目标未定或骨架近空先聊目标；AI 协助把诉求收成一句话目标（≤30字）
clarifying 推进目标已定，缺口在收敛、方案在竞争正常整理；优先追问缺口；方案竞争到唯一采用
reflected 已沉淀结论齐了、缺口清了——继续做不影响，但认知已固化点「归档」：从活跃列表折叠，数据永久保留
archived30 天无活动也会自动标记仪表盘勾「含已沉淀」可见；「恢复」随时拉回

⑦ 多 harness 协作规则

场景规则
共享板项目身份 = 目录。两个工具在同一目录工作 → 同一块板，互相可见全部沉淀
接手礼仪后接手的工具先 mind_board_query 看板子再动手——钩子注入的状态行就是为此设计的
竞争收敛两边对同一问题给出不同结论 → 后写的 supersedes 前写的（板子保留最新认知）；若真是并立的两案 → 都进 plans 竞争
缺口责任谁发现谁立，谁都能关；跨工具的缺口（“待另一工具确认”）写明对象
参与者可见项目档案 harnesses[] 记录全部参与者；图标环/面板/仪表盘按此归属显示
